# Balance BMS BLE通信プロトコル解析

対象: Balance BMS v1.0.30（`com.inuker.bluetooth.junhengbao`、versionCode 10030）
解析方法: JADX 1.5.3 による静的解析（REA の Android 解析と同じエンジン）。実機での確認はまだしていません。
主な根拠ファイル（元アプリを JADX で逆コンパイルしたときのクラス名。逆コンパイル結果はこのリポジトリには含めていません）:
- `bluetooth/data/BluetoothRegulate.java` … 接続、GATT、受信フレームの組み立て
- `com/inuker/bluetooth/data/CreateCtrDataHelper.java` … 送信コマンドの生成
- `com/inuker/bluetooth/data/DataAnalysisHelper.java` … 受信データの振り分け
- `com/inuker/bluetooth/data/DeviceWorkInfo.java` … フィールドの解析
- `bluetooth/NEWBLE/LiveDataActivity.java`, `SetValueActivity.java`, `MainControlActivity.java`, `ZhuDongJunHengActivity.java`

## 1. GATT構成

| 用途 | Service UUID | Characteristic UUID | 操作 |
|---|---|---|---|
| データ受信 | `0000fff0-0000-1000-8000-00805f9b34fb` | `0000fff1-…-00805f9b34fb` | Notify |
| データ送信 | 同上 | `0000fff2-…-00805f9b34fb` | Write（Notifyも有効化。ボーレート応答に使う） |
| ATコマンド（名前変更など） | 同上 | `0000fff3-…-00805f9b34fb` | Write |
| B35系の認証 | 同上 | `0000fffA-…-00805f9b34fb` | Write / Read |
| モジュール認証・バージョン | `02f00000-0000-0000-0000-00000000fe00` | `…ff04`（Notify/Write）, `…ff05`（認証キー Write/Read） | |
| BLEモジュールOTA | 同上 `…fe00` | `…ff01`（Write No Rsp）, `…ff02`（Notify） | |

`fe00` サービスがあれば「B40モジュール」（`isB40 = true`）とみなされます。

### 接続シーケンス
1. 接続（リトライ2回、タイムアウト 40秒、サービス探索タイムアウト 10秒）
2. MTU 512 を要求
3. `fff1` と `fff2` の Notify を有効化（B40 の場合は `ff04` と `ff02` も）
4. Notify 有効化に成功したら:
   - `ff05` に ASCII `"HiLink"` を書き込み → `ff05` を読む。`0100` が返れば認証OK
     → `ff04` に `AT+VER=?\r\n` を送信、`fff3` に `AT+BAND=?` を送信
   - 時刻同期: `D2 10 00D4 0003 YY MM DD hh mm ss CRC`（年は 2000 を引いた値）
5. 以降は **5秒ごと** に運転データ（レジスタ 0〜61）を読む（`MainControlActivity.startSendTimer`）

## 2. フレーム形式（Modbus RTU）

16進文字列で組み立て、バイト列にして `fff2` へ書き込みます。CRC は **Modbus CRC16**（初期値 0xFFFF、多項式 0xA001）で、下位バイトが先です。

| 種類 | 形式 | 説明 |
|---|---|---|
| 読み出し | `D2 03 [開始アドレス 2B] [個数 2B] [CRC 2B]` | スレーブアドレス 0xD2 |
| 応答 | `D2 03 [バイト数 1B] [データ…] [CRC]` | |
| 1レジスタ書き込み | `D2 06 [アドレス 2B] [値 2B] [CRC]` | 応答は同じ形でエコー |
| 複数レジスタ書き込み | `D2 10 [開始 2B] [個数 2B] [データ…] [CRC]` | **注意: 標準Modbusにある「バイト数」フィールドが無い**（独自仕様） |
| 応答（0x10） | `D2 10 [開始 2B] [個数 2B] [CRC]` | |
| 実容量（32bit）読み出し | `81 03 010B 0002 CRC` | スレーブアドレス 0x81 |
| 実容量 書き込み | `81 10 010B 0002 [値 4B] CRC` | 応答の先頭は `5110` |
| BMSファームウェア更新 | 先頭 `81 10`（bin）/ 応答 `A5FF`（s19） | 詳細は 7章 |

受信側は Notify で届いた断片を文字列バッファにつなげ、先頭が `D203` / `D206` / `D210` / `A5FF` / `5110` のどれかになるまで1バイトずつ読み捨てて同期します。`D203` は 3バイト目のバイト数から長さを決めて CRC を確認します。

**電流の向きについて**: 元アプリは電流の符号をそのまま表示するだけで、どちらが充電かを明示していません。

BMS Japan では電流は大きさだけを表示し、向きはレジスタ47（状態）で示しています。

- 元アプリは 4 ページ（28 件）ずつ読み、総件数に達するか、番号 0 の記録が出たら終わりにします。

## 6. パスワードの扱い
アプリはレジスタ 201〜203 から **パスワードを平文で読み出し、アプリ側で照合**しています（`MainControlActivity` 391〜407行目）。値が `123456` なら確認を省略します。BMS側では認証していないため、作り直す際は同じ動き（設定画面の前にパスワード確認）を再現すれば互換になります。

## 7. ファームウェア更新（参考）
- BMS本体: assets の `UartTFT_Flash.bin` / `2118.bin` / `2121.bin` / `2322.bin` などを `81 10` フレームで分割送信（`0F01`〜`0F05` が手順コード: 結果, ファイル送信, 終了, 送信応答, 状態確認）。s19 形式は `A5FF` 応答。
- BLEモジュール: `fe00/ff01` に Write No Response、`ff02` で応答。
- 失敗すると機器が使えなくなるおそれがあるため、最初の作り直しでは対象外にすることをおすすめします。

## 8. 未確認の点
- 実機での動作確認はしていません。値の変換（特に 131〜136, 161/162, 167）は画面のラベルと照らし合わせて確定させる必要があります。
- 通信モジュールが違う機種（WiFi/4G 版、`wifiActivity` 配下）は Aliyun IoT クラウド経由で、BLE とは別の経路です。
